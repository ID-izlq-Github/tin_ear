# TinEar

**本地音频盲测工具 —— 你能听出 MP3 码率的区别吗？**

A local blind test for MP3 bitrate perception.

TinEar 把你自己音乐库里的无损片段切成 15 秒，生成不同码率的 MP3 版本，
再把**无损版**和**压缩版**做成一组等响度、精确对齐的 A/B 让你盲听 ——
作答前你不知道哪边是无损，程序也不告诉你码率、文件名、编码器（每题作答后可以点「查看答案」揭晓本题）。

---

## 技术栈

后端是 Python（FastAPI + Uvicorn）；音频处理直接用系统的 **ffmpeg / ffprobe**，配 numpy / scipy / pyloudnorm /
soundfile 做解码、对齐与响度分析；前端是**原生 HTML/CSS/JS**（无框架、无构建步骤、不需要 Node），
播放走浏览器 Web Audio API（AudioContext 固定 48 kHz）。**没有数据库** —— 库信息是一个 JSON，
测试状态放在内存里，所以重启后端就清空。

- **不需要**：Node / npm、编译器或系统库、数据库、Docker
- 服务默认绑在本机，浏览器访问 <http://localhost:8000>（绑 `0.0.0.0` 只是为了虚拟机 + 宿主机浏览器，
  见下面的「安全提示」）；具体依赖见下一节

> 本项目是在 **WSL Ubuntu + Windows 浏览器**下开发和验证的（WSL 里没有音频设备，必须在 Windows 侧播放），
> 代码本身跨平台。

## 前置条件

- **Python 3.10+**（开发与实测用 3.12）
- **系统已安装 `ffmpeg` 与 `ffprobe`**（实测 6.1.1）—— 本项目不打包也不自动安装它们，
  启动时会检查，缺失会直接报错。装法（任选一条，装完**重开终端**让 PATH 生效）：
  - Windows：`winget install --id Gyan.FFmpeg`，或 `scoop install ffmpeg` / `choco install ffmpeg`
  - macOS：`brew install ffmpeg`
  - Ubuntu / Debian / WSL：`sudo apt install ffmpeg`
  - 自检：终端里 `ffmpeg -version` 与 `ffprobe -version` 都能跑通即可
- Python 依赖全是 wheel（`soundfile` 自带 libsndfile），不需要编译器或系统库

## 快速开始

### 方式一：venv（通用，推荐给新同学）

**macOS / Linux / WSL**

```bash
git clone https://github.com/ID-izlq-Github/tin_ear.git && cd tin_ear
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python -m uvicorn app:app --host 0.0.0.0 --port 8000 --workers 1
```

**Windows（PowerShell / CMD）**

```pwsh
git clone https://github.com/ID-izlq-Github/tin_ear.git
cd tin_ear
python -m venv .venv
.venv\Scripts\python -m pip install -r requirements.txt
.venv\Scripts\python -m uvicorn app:app --host 127.0.0.1 --port 8000 --workers 1
```

然后在浏览器打开 <http://localhost:8000>。

> - `--workers 1` 不是可选项：测试会话保存在内存里，起多个 worker 会出现"这个进程没这个会话"的随机报错。
> - **WSL 用户**：服务在 WSL 里、浏览器在 Windows 侧，请用 `--host 0.0.0.0`（只绑 `127.0.0.1` 时
>   Windows 侧经常连不上）；原生 Windows 用上面的 `127.0.0.1` 即可（更安全）。
> - 首次盲测要等几秒生成音频，页面会显示**进度条**；之后的重复测试是秒开（细节见「使用流程」）。

### 方式二：Makefile（作者自用，conda 环境名 `tin_ear`，仅 macOS / Linux / WSL）

```bash
make install     # 安装依赖（解释器自动挑选：项目内 .venv → conda 环境 tin_ear → python3）
make run         # 前台启动（Ctrl+C 停止）
make run-bg      # 后台启动，日志写 data/server.log
make stop        # 停止
make test        # 跑自动化测试（约 1 分钟）
make help        # 看全部目标与当前使用的解释器
```

`PY` / `HOST` / `PORT` 都可以覆盖，例如 `make run PY=.venv/bin/python HOST=127.0.0.1`。

### 安全提示（两种方式都适用）

这是一个**本地单用户**工具，接口**没有任何认证** —— 谁能访问到这个端口，谁就能看你的音频库、删你的文件、
替你开始测试。方式一在 macOS / Linux / WSL 上用的是 `--host 0.0.0.0`（为了 WSL / 虚拟机 + 宿主机浏览器），
这等于对局域网开放：

- 家里的单人机器无所谓（Windows 防火墙默认还会拦外部入站）；
- 在公共 Wi-Fi、宿舍网、公司网里请改用 `--host 127.0.0.1`（WSL 里浏览器在 Windows 侧连不上时，
  可以用 SSH 端口转发 `ssh -L 8000:127.0.0.1:8000`，或临时共享），或者自行加一层反向代理 + 鉴权。

### 本项目对环境的影响

- 运行时临时文件（上传落盘、ffmpeg 中间文件、测试合成音频）都写在项目内 `data/tmp/`：用 `make`
  时由 `TMPDIR` 指定，直接 `python -m uvicorn` 时由 `app.py` 启动时设置 `tempfile.tempdir` 兜底 ——
  这样这些动辄几百 MB 的草稿一来看得见、二来删一个 `data/tmp` 就干净了（界面按钮/`make clean` 同理）。
- pip 下载缓存**不重定向**，走 pip 自己的默认位置（Linux/macOS `~/.cache/pip`，Windows
  `%LOCALAPPDATA%\pip\Cache`）；要清就 `python -m pip cache purge`。
  （旧版本曾用 `PIP_CACHE_DIR` 把它顶到项目内 `.pip-cache/`，已取消：那只是把缓存换个地方，
  还要额外解释一遍。）
- 依赖只装进你自己的虚拟环境/conda 环境（本项目从不 `apt install`、不 `npm -g`、不 `pip --user`）。
- `requirements.lock.txt` 是作者机器上实测通过的完整环境快照（`pip list --format=freeze` 的输出），
  仅供参考与复现问题；正常安装请用 `requirements.txt`。

## 使用流程

1. **导入音频**：点「导入音频」选文件。只接受无损格式（FLAC / WAV / AIFF / ALAC / WavPack / TTA），
   要求采样率 ≥ 44.1 kHz、时长 ≥ 30 秒。导入后统一转成 48 kHz 立体声 FLAC。
   MP3 / AAC / OGG / Opus 会被拒绝并给出明确原因。同一段音频（即使换了容器格式）按内容哈希去重。
   带内嵌封面的文件也照常导入（封面在入库时被丢掉，不会再触发编码错误）。
2. **选素材**：勾选 1～3 段，选「快速（6 题 · 每档 1 题）」或「详细（22 题 · 每档 2 题）」。
   **选曲建议**：优先用配器复杂、动态强烈的曲目；安静、单调或本身就很"糊"的段落，
   即使在 32 kbps 下也可能听不出差别 —— 那样测出来的"听不出"说明不了任何事。
3. **开始盲测**：首次会截取片段、并发生成并校准压缩版（详细 22 题首轮实测约 4 秒，
   生成过程中会显示进度条；单核机器串行约 16 秒）。之后同素材再测**直接复用缓存**
   （实测 0.01 秒），界面会显示「新生成 N 段 / 复用 M 段」。
4. **听**：点 A / B 试听（循环播放，切换时**保持播放位置**），然后选「A 更好 / B 更好 / 听不出」。
   **题目顺序每轮随机，安慰剂题也混在中间** —— 第几题不代表任何信息，只能每题都真听。
   测试音频已等响归一化到 **−18 LUFS**（比广播标准响 5 dB），A/B 下面还有一条**试听音量滑条**
   （`−40 dB…0 dB`，`↑/↓` 键 ±2 dB）—— 它只改监听响度、A/B 完全同步，不影响判定，纯粹是舒适度。
5. **确认后再走**：作答后**停在本题** —— 你的选择会高亮、其余变暗，显示「已记录：B 更好」。
   点「查看答案」会揭晓**两侧的具体身份**（例如 `A：无损 / B：MP3 96 kbps`）以及你是否选对；
   默认不自动揭晓，避免对后面几题产生反馈偏置。**首答即最终**：改选项不算数（否则先看答案再改就能刷分）。
   再点「下一题 →」继续（最后一题是「查看结果 →」）。
6. **看结果**：整体 + 分档的正确率、p 值与判定、逐档明细、安慰剂「听不出」比例、一句话结论。

键盘（测试页）：`1` = A 更好、`2` = B 更好、`3` = 听不出、`A`/`B`/空格 = 切换试听、回车或空格 = 下一题。
音频没载入完时三个选项是禁用的，避免在没听到声音时作答（保证反应时间有效）。

### 听测注意事项（重要）

- 关闭音效增强 / 空间音频 / 音量均衡（Windows：音效增强、Dolby、EQ、空间音频）。
- 系统音量固定，测试过程中不要再调；要改响度就用页面里的**试听音量滑条**（它不影响判定）。
- 用同一副耳机/音箱，从低码率题开始适应；疲劳了就停。
- 若页面顶部出现"设备实际采样率不是 48 kHz"的黄色警告，说明浏览器正在重采样，可能削弱可听差异。

## 数据与存储

```
data/
  library/   持久：48 kHz FLAC 母版 + index.json（含源文件元信息）
  cache/     持久：<audio_id>/meta.json、seg_*.flac，以及 <audio_id>/stimuli/v{N}/
             （index.json + 成对的 *_ll.wav / *_mp3.wav；N = app.py 的 STIMULI_ALGO_VERSION）
  session/   临时：当前测试的硬链接（指向 cache 里的测试音频），/api/end 或重启即清
  tmp/       临时：上传落盘与 ffmpeg 中间文件，重启即清
```

- **每个 (片段, 码率) 组合只生成一次，生成过就永久复用**（没有任何淘汰逻辑），所以体积有上限：
  两套阶梯的并集 11 档 × 2 个片段 + 2 个安慰剂 = 46 个 WAV ≈ **267 MB/首**。
  实际占多少取决于你跑过哪些模式：**只跑快速模式约 70 MB/首**，详细模式实测 **245.8 MB/首**
  （界面上的数字是 MiB 口径）。界面上的「清理测试音频缓存」会清空 `data/cache/`（库里的音频不受影响）。
- 测试音频是否命中缓存，取决于**这一轮题表需要哪些 (片段, 码率) 组合**；同一批素材 + 同一模式
  + 无论勾选顺序，集合都一样 → **100% 复用**（换模式时能复用多少，见下一小节）。
- `/api/end` 只删 session 里的硬链接，不动测试音频缓存 —— 所以「再测一次」几乎瞬时开始
  （实测第二轮 `新生成 0 / 复用 22`，0.01 秒）。
- **只有尚未完成的测试**会阻止删除（返回 409）；答完全部题目、或结束测试之后就能删。
  离开测试页、点「再测一次」、关闭标签页都会自动结束会话，不会留下"进行中的引用"。
- session 目录里是 cache 的**硬链接**，所以它不额外占磁盘（用 `du` 看会把同一份数据算两次，别被吓到）；
  只有"cache 与 data 不在同一个文件系统"时才会退化成复制，那种情况下一轮约 250 MB，结束测试即释放。

### 换模式重测会复用多少

以单首、源长 ≥ 60 秒的素材为例（同一批素材、不管勾选顺序）：

| 这一轮 | 下一轮 | 复用 | 新生成 | 体感 |
|---|---|---|---|---|
| 快速（6 题） | 快速 | 6 | 0 | 0.01 秒 |
| 详细（22 题） | 详细 | 22 | 0 | 0.01 秒 |
| 快速（6 题） | 详细（22 题） | 5 | 17 | 一轮冷启动（约 4 秒） |
| 详细（22 题） | 快速（6 题） | 5 | **1** | 约 0.7 秒（只差 224 kbps 那一对） |

**先详细再快速几乎就是秒开**；反过来必须先补 17 个组合 —— 因为详细模式的阶梯是 10 档 × 2 个片段，
而快速模式的 5 档只覆盖了其中 5 个组合。两种顺序最终生成的总量一样（都是 23 个条目），
差别只是"等待"发生在哪一轮。想连"先快后详"也秒开，就得首次把两套阶梯的并集全部生成好
（磁盘 +约 190 MB/首）—— 本项目的选择是**按需生成**：只用快速模式的人不必为 10 档全档买单。

### 想清理磁盘占用怎么办

**先看占用**：库页面下方那行小字就写着「测试音频缓存 X MB · 临时文件 Y KB」。想在命令行看，
用 `make size`（方式二）或 `du -sh data/*`（macOS / Linux / WSL）、
`Get-ChildItem data | Select-Object Name, Length`（Windows PowerShell）。

清理有**两个入口，任何安装方式都适用**：界面按钮（Windows 用户也不用开终端），或者直接删项目内的目录。

| 位置 | 是什么 | 怎么清 | 代价 | 典型占用 |
|---|---|---|---|---|
| `data/cache/` | 片段 + 测试音频缓存（**最大的一块**） | 界面上的「清理测试音频缓存」按钮，或 `make clean-cache`，或直接删 `data/cache` | 下次开测重新生成：快速模式约 1 秒、详细 22 题约 4 秒 | 详细模式跑满约 **245 MB/首**；只跑快速模式约 **70 MB/首** |
| `data/tmp/` | 上传落盘与 ffmpeg 中间文件的草稿区 | **什么都不用做**（后端每次启动自动清空），或删 `data/tmp` | 无 | 平时接近 0；跑过测试可能到几百 MB |
| `data/session/` | 进行中测试的硬链接（**不额外占空间**） | **什么都不用做**（结束测试 / 重启即清），或删 `data/session` | 会打断进行中的测试 | 跨文件系统回退成复制时才约 250 MB |
| `__pycache__/`、`.pytest_cache/` | Python / pytest 运行缓存 | 删掉即可 | 无 | 共约 400 KB |
| pip 下载缓存 | pip 自己的位置（**不在项目里**） | `python -m pip cache purge` | 下次 install 重新下载 | — |
| `data/library/` | **你自己导入的音频母版** | ❌ 别删（要删请用界面上的「删除」按钮，会同时清掉它的缓存） | 重新导入 | 视曲目长度，无损母版通常 30～50 MB/首 |

方式一（venv）用户的等价命令（在项目根目录执行）：

```bash
# macOS / Linux / WSL
rm -rf data/cache data/tmp data/session .pytest_cache
find . -name __pycache__ -type d -prune -exec rm -rf {} +
```

```pwsh
# Windows PowerShell
Remove-Item -Recurse -Force data\cache, data\tmp, data\session, .pytest_cache -ErrorAction SilentlyContinue
Get-ChildItem -Recurse -Directory -Filter __pycache__ | Remove-Item -Recurse -Force
```

用 Makefile 的话一次清完可重建项就是 `make clean`（服务在跑时会提醒你先 `make stop`）。

其余细节：

- **界面上那个「清理测试音频缓存（70.0 MB）」按钮只管 `data/cache/`** —— 括号里的数字就是它要释放的量，
  它不碰 `data/tmp`（草稿区）和 `data/library`（你的音频）。页面下方那行小字会同时显示两个数字：
  「测试音频缓存 70.0 MB（按钮释放的就是它）· 临时文件 8 KB（后端每次启动自动清空）」。
- 跑测试才会往 `data/tmp/` 堆东西（合成音频几十到几百 MB），所以项目里加了 `pytest.ini`：
  `tmp_path_retention_policy = failed` + `tmp_path_retention_count = 1` —— 全绿时自动删掉，
  只在失败时保留那一轮供排查。
- pip 缓存不在项目里，本项目也不会去动它；真要清用 `python -m pip cache purge`
  （会一并清掉其他项目的 pip 缓存，通常没必要）。
- **也不要图省事用 `git clean -xfd`**：`data/` 在 `.gitignore` 里，它会把 `data/library/`
  （你自己导入的音频母版）一起删掉。要清理请用上面表里的路径逐个删。

## 设计要点（为什么结果可信）

| 关注点 | 做法 |
|---|---|
| **响度线索** | 两路各自按 integrated loudness 独立增益到 **−18 LUFS** → 响度差恒为 **0**；再施加以对为单位的**共同**线性衰减把 True Peak 压到 ≤ −1 dBTP（实测 −5.3 dBTP）。全程**不使用限幅器**（限幅是非线性处理，会在低码率制造与 MP3 无关的失真线索） |
| **时间对齐** | FFT 互相关粗估 + 逐点平均绝对差精修，正负延迟都覆盖；两路统一裁到**精确 720000 采样**（48 kHz × 15 s 恰好 = 625 个 MP3 帧） |
| **信息泄漏** | `/api/audio` 只用随机不透明 token；响应键集合固定；两路 `Content-Length` 恒等。**作答之前**，码率、编码器、文件名、是否安慰剂都不出现在前端；作答之后才用同一题的 `reveal` 揭晓两侧身份 |
| **顺序预判** | 真实题与安慰剂题**一起打乱**（`SHUFFLE_ALL_QUESTIONS`）。"第几题"既不指向码率高低，也不指向"这题其实没差别"；无脑按「听不出」会把真实题全答错 |
| **只看已作答的题** | 揭晓只返回本题两侧身份，不含后面的题目；作答**首答即最终**，堵死"先看答案再改分" |
| **统计口径** | 三选一是 1/3 的瞎猜基线（**不是 50%**），显著性用单侧**精确二项检验**（H0: p = 1/3）；Wilson 95% 区间只作描述性参考。每档 < 3 题一律标「样本不足，无法判定」 |
| **安慰剂** | 1～2 道题的 A/B 是**同一片段的两份无损拷贝**，混在题目中。若你在这类题上仍"听出更好的一边"，说明存在瞎猜倾向，结论会提示 |
| **片段选择** | 15 秒窗 / 5 秒步长滑动，按「响度标准差 + 谱通量 + 瞬态密度 − 静音比例」四分量 z-score 加权选段，偏好动态大、瞬态多、不安静的段落 |
| **缓存复用** | 测试音频按 `(音频, 片段, 码率)` 组合持久缓存、永不淘汰，题表只由「模式 + 素材集合」决定（选曲顺序被显式排序抹平）→ 同素材重测 **100% 复用**，且**按需生成**：只跑快速模式的人不必为 10 档全档买单 |
| **生成并发** | 单题生成约 0.70 s（响度+对齐 0.46 s、ffmpeg 编解码 0.25 s），按 CPU 核数并发（默认封顶 8）后 22 题从 15.3 s 降到 3.9 s；生成期间前端轮询进度，界面有进度条 |

## 测试

```bash
make test    # 方式二：68 项，约 1 分钟（需要先 make install-dev 装过 pytest/httpx）
```

方式一（venv）用户没有 `make` 也能跑，关键是别把临时文件丢到系统 temp 里：

```bash
# macOS / Linux / WSL
TMPDIR="$PWD/data/tmp" python -m pytest -q
```

```pwsh
# Windows PowerShell
$env:TMPDIR="$PWD\data\tmp"; python -m pytest -q
```

（`pytest`/`httpx` 用 `python -m pip install -r requirements-dev.txt` 装。）

想确认安装是否完好，跑一遍这个就够。逐项覆盖范围与设计原因属于开发细节，见 [AGENTS.md](AGENTS.md) §14。
按上面的命令跑（带 `TMPDIR`）时，测试产物全部落在项目内的 `data/tmp/`，不会写系统 temp。

## 怎么读结果

结果页顶上是一张**结论卡**，底下是两张表和一段可折叠的说明：

- **瞎猜基线是 1/3**，不是 50%：三个选项里只有一个是"无损那侧"，闭着眼睛乱选也有约 33% 的平均正确率。
  结论卡上的徽章就按这个基线判定：`显著高于 1/3`（绿）/ `无显著差异`（灰）/ `样本不足`（黄）。
- **逐档只有 1～2 题时没有统计意义** —— 表格里 3 题以下一律标「样本不足」（n=1 时最小的 p 就是 1/3，
  结构上不可能显著）。默认详细模式每档 2 题仍然偏少：要在 80% 检验功效下做判断（假定真听出率 0.8），
  **大约需要每档 7 题**。所以先看结论卡的**总体**，再看三个分档 chip（详细模式分档 n = 10 / 6 / 4）。
- 真正能说明"听不出"的信号是**安慰剂题**上的表现：如果安慰剂上你也常常选"更好的一边"，
  那前面那些"听出差异"很可能只是猜测 —— 结论卡会把这一行标成黄色。
- 需要工具细节（Wilson 区间、p 值含义、每档 < 3 题为何无法判定）就展开「统计口径与样本量说明」，
  里面还有一段可复制的纯文本结论。
- 想得到更硬的结论：把 `app.py` 顶部的 `DETAILED_TEST_TOTAL`（或 `SHORT_TEST_TOTAL`）调大 ——
  每档题数随之增加，码率阶梯会自动循环，不需要改任何 API。

## 常见问题

**导入后没有声音？** 如果后端跑在 WSL 等没有音频设备的虚拟机里，是正常的 —— 在宿主机浏览器里打开
<http://localhost:8000> 即可。

**导入被拒绝？** 界面会写原因（有损格式 / 采样率 < 44.1 kHz / 时长 < 30 秒），对着改就行。

**封面会不会出问题？** 不会。导入与切片都显式只取音频流，内嵌封面（附带的图片流）会被丢掉。

**首次开始测试要等多久？换模式呢？** 详细 22 题首轮约 4 秒（单核串行约 16 秒，生成时页面有进度条）；
之后同素材直接复用缓存（0.01 秒，界面显示「新生成 0 段 / 复用 22 段」）。换模式的复用情况见
「换模式重测会复用多少」——**先详细再快速几乎秒开**，反过来要补 17 个组合（约 4 秒）。

**点「查看答案」没反应 / 按钮消失了？** 那是浏览器还在跑缓存里的旧脚本（旧脚本读的字段已经改名）。
现在 `/` 与 `/static/*` 都带 `Cache-Control: no-cache`，页面用 `?v=N` 引用资源，正常情况下刷新一次就好；
万一还遇到，按 **Ctrl+Shift+R** 强刷即可 —— 揭晓函数本身也会给出这句提示，不会再静默失败。

**"会话已失效"？** 后端重启或超过 2 小时未完成会丢弃会话，重新开始即可。

**磁盘占用越来越大，怎么清？** 见上面的「想清理磁盘占用怎么办」。最快的办法：用界面上的
「清理测试音频缓存」按钮（它清的是最大那块 `data/cache/`），然后删掉项目里的 `data/tmp`、
`data/session` —— 不用 `make` 也能做（Windows 同理）。`data/library/` 里的音频不要动。

## 它不做什么

下面这些是**刻意的取舍**，不是"还没做完"：

- **只测 MP3**：不做 AAC / Opus 对比，也不做 192 kHz 差异测试。
- **片段固定 15 秒**：长度必须一致，否则盲测的统计会被污染。
- **不是 ABX**：这里是「无损 vs 压缩」的 A/B/听不出 三选一，不是经典 ABX 双盲；想要更硬的结论不靠新功能，
  靠题量 —— 见「怎么读结果」里"把 `DETAILED_TEST_TOTAL` 调大"那条。
- **没有账号、多用户、历史记录**：库信息就是一个 JSON，测试状态在内存里，重启后端即清空。

完整的取舍清单（含维护者视角的理由）在 [AGENTS.md](AGENTS.md) §10。
