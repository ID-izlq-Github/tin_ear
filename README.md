# TinEar

**本地音频盲测工具 —— 你能听出 MP3 码率的区别吗？**

A local blind test for MP3 bitrate perception.

TinEar 把你自己音乐库里的无损片段切成 15 秒，生成不同码率的 MP3 版本，
再把**无损版**和**压缩版**做成一组等响度、精确对齐的 A/B 让你盲听 ——
作答前你不知道哪边是无损，程序也不告诉你码率、文件名、编码器（每题作答后可以点「查看答案」揭晓本题）。

---

## 前置条件

- **Python 3.10+**（开发与实测用 3.12）
- **系统已安装 `ffmpeg` 与 `ffprobe`**（实测 6.1.1）—— 本项目不打包也不自动安装它们，
  启动时会检查，缺失会直接报错
- Python 依赖全是 wheel（`soundfile` 自带 libsndfile），不需要编译器或系统库

## 快速开始

### 方式一：venv（通用，推荐给新同学）

```bash
git clone <你的仓库地址> && cd tin_ear
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python -m uvicorn app:app --host 127.0.0.1 --port 8000 --workers 1
```

然后在浏览器打开 <http://localhost:8000>。

### 方式二：Makefile（作者自用，conda 环境名 `tin_ear`）

```bash
make install     # 安装依赖（解释器自动挑选：项目内 .venv → conda 环境 tin_ear → python3）
make run         # 前台启动（Ctrl+C 停止）
make run-bg      # 后台启动，日志写 data/server.log
make stop        # 停止
make test        # 跑自动化测试（约 1 分钟）
make help        # 看全部目标与当前使用的解释器
```

`PY` / `HOST` / `PORT` 都可以覆盖，例如 `make run PY=.venv/bin/python HOST=127.0.0.1`。

> **安全提示**：这是一个**本地单用户**工具，接口不带任何认证。默认绑 `0.0.0.0` 是为了方便
> （虚拟机里的服务 + 宿主机浏览器访问）；如果机器在共享或不可信网络上，请用 `HOST=127.0.0.1`
> 启动，或自行加反向代理与鉴权。

### 作者的验证环境（WSL + Windows 浏览器）

本项目在 WSL Ubuntu 下开发，用 Windows 侧浏览器访问 `http://localhost:8000`，因此文档里保留了一些
Windows 相关注意事项（见「听测注意事项」）。WSL 里没有音频设备是正常的，必须在 Windows 侧播放。

### 本项目对环境的影响

- 默认**不改动**系统与其他项目：pip 下载缓存写项目内 `.pip-cache/`，运行时临时文件全部写项目内
  `data/tmp/`（`TMPDIR` + `tempfile.tempdir` 双重保证），不写系统 temp、不写 `~/.cache`。
- 依赖只装进你自己的虚拟环境/conda 环境（本项目从不 `apt install`、不 `npm -g`、不 `pip --user`）。
- `requirements.lock.txt` 是作者机器上实测通过的完整环境快照（`pip list --format=freeze` 的输出），
  仅供参考与复现问题；正常安装请用 `requirements.txt`。

## 使用流程

1. **导入音频**：点「导入音频」选文件。只接受无损格式（FLAC / WAV / AIFF / ALAC / WavPack / TTA），
   要求采样率 ≥ 44.1 kHz、时长 ≥ 30 秒。导入后统一转成 48 kHz 立体声 FLAC。
   MP3 / AAC / OGG / Opus 会被拒绝并给出明确原因。同一段音频（即使换了容器格式）按内容哈希去重。
   带内嵌封面的文件也照常导入（封面在入库时被丢掉，不会再触发编码错误）。
2. **选素材**：勾选 1～3 段，选「快速（6 题 · 每档 1 题）」或「详细（22 题 · 每档 2 题）」。
   **选曲建议**：优先用配器复杂、动态强烈的曲目；安静、单调或本身就很"糊"的段落，
   即使在 32 kbps 下也可能听不出差别 —— 那样测出来的"听不出"说明不了任何事。
3. **开始盲测**：首次会截取片段、生成并校准压缩版（22 题首轮实测约 16 秒），
   之后同素材再测**直接复用缓存**（实测 0.01 秒），界面会显示「新生成 N 个 / 复用 M 个」。
4. **听**：点 A / B 试听（循环播放，切换时**保持播放位置**），然后选「A 更好 / B 更好 / 听不出」。
   **题目顺序每轮随机，安慰剂题也混在中间** —— 第几题不代表任何信息，只能每题都真听。
5. **确认后再走**：作答后**停在本题** —— 你的选择会高亮、其余变暗，显示「已记录：B 更好」。
   点「查看答案」会揭晓**两侧的具体身份**（例如 `A：无损 / B：MP3 96 kbps`）以及你是否选对；
   默认不自动揭晓，避免对后面几题产生反馈偏置。**首答即最终**：改选项不算数（否则先看答案再改就能刷分）。
   再点「下一题 →」继续（最后一题是「查看结果 →」）。
6. **看结果**：整体 + 分档的正确率、p 值与判定、逐档明细、安慰剂「听不出」比例、一句话结论。

键盘（测试页）：`1` = A 更好、`2` = B 更好、`3` = 听不出、`A`/`B`/空格 = 切换试听、回车或空格 = 下一题。
音频没载入完时三个选项是禁用的，避免在没听到声音时作答（保证反应时间有效）。

### 听测注意事项（重要）

- 关闭音效增强 / 空间音频 / 音量均衡（Windows：音效增强、Dolby、EQ、空间音频）。
- 系统音量固定，测试过程中不要再调。
- 用同一副耳机/音箱，从低码率题开始适应；疲劳了就停。
- 若页面顶部出现"设备实际采样率不是 48 kHz"的黄色警告，说明浏览器正在重采样，可能削弱可听差异。

## 数据与存储

```
data/
  library/   持久：48 kHz FLAC 母版 + index.json（含源文件元信息）
  cache/     持久：<audio_id>/meta.json、seg_*.flac、stimuli/v1/*.wav
  session/   临时：当前测试的硬链接，/api/end 或重启即清
  tmp/       临时：上传落盘与 ffmpeg 中间文件，重启即清
```

- 缓存体积上限约 **每首 250 MB**（详细模式下 2 个片段 × 10 档 × 2 个文件 + 2 个安慰剂，实测 245.8 MB）。
  界面上的「清理刺激缓存」会清空 `data/cache/`（库里的音频不受影响，下次测试重新生成）。
- `/api/end` 只删 session 里的硬链接，不动刺激缓存 —— 所以「再测一次」几乎瞬时开始
  （实测第二轮 `新生成 0 / 复用 22`，0.01 秒）。
- **只有尚未完成的测试**会阻止删除（返回 409）；答完全部题目、或结束测试之后就能删。
  离开测试页、点「再测一次」、关闭标签页都会自动结束会话，不会留下"进行中的引用"。
- 测试进行中点「清理刺激缓存」是安全的：session 里是硬链接，已载入的音频照常播放；
  只是那轮结束后 session 目录会临时占用约 60 MB，结束测试即释放。

## 设计要点（为什么结果可信）

| 关注点 | 做法 |
|---|---|
| **响度线索** | 两路各自按 integrated loudness 独立增益到 −23 LUFS → 响度差恒为 **0**；再施加以对为单位的**共同**线性衰减把 True Peak 压到 ≤ −1 dBTP。全程**不使用限幅器**（限幅是非线性处理，会在低码率制造与 MP3 无关的失真线索） |
| **时间对齐** | FFT 互相关粗估 + 逐点平均绝对差精修，正负延迟都覆盖；两路统一裁到**精确 720000 采样**（48 kHz × 15 s 恰好 = 625 个 MP3 帧） |
| **信息泄漏** | `/api/audio` 只用随机不透明 token；响应键集合固定；两路 `Content-Length` 恒等。**作答之前**，码率、编码器、文件名、是否安慰剂都不出现在前端；作答之后才用同一题的 `reveal` 揭晓两侧身份 |
| **顺序预判** | 真实题与安慰剂题**一起打乱**（`SHUFFLE_ALL_QUESTIONS`）。"第几题"既不指向码率高低，也不指向"这题其实没差别"；无脑按「听不出」会把真实题全答错 |
| **只看已作答的题** | 揭晓只返回本题两侧身份，不含后面的题目；作答**首答即最终**，堵死"先看答案再改分" |
| **统计口径** | 三选一是 1/3 的瞎猜基线（**不是 50%**），显著性用单侧**精确二项检验**（H0: p = 1/3）；Wilson 95% 区间只作描述性参考。每档 < 3 题一律标「样本不足，无法判定」 |
| **安慰剂** | 1～2 道题的 A/B 是**同一片段的两份无损拷贝**，混在题目中。若你在这类题上仍"听出更好的一边"，说明存在瞎猜倾向，结论会提示 |
| **片段选择** | 15 秒窗 / 5 秒步长滑动，按「响度标准差 + 谱通量 + 瞬态密度 − 静音比例」四分量 z-score 加权选段，偏好动态大、瞬态多、不安静的段落 |

## 怎么读结果

结果页顶上是一张**结论卡**，底下是两张表和一段可折叠的说明：

- **瞎猜基线是 1/3**，不是 50%：三个选项里只有一个是"无损那侧"，闭着眼睛乱选也有约 33% 的平均正确率。
  结论卡上的徽章就按这个基线判定：`显著高于 1/3`（绿）/ `无显著差异`（灰）/ `样本不足`（黄）。
- **逐档只有 1～2 题时没有统计意义** —— 表格里 3 题以下一律标「样本不足」（n=1 时最小的 p 就是 1/3，
  结构上不可能显著）。默认详细模式每档 2 题仍然偏少：要在 80% 检验功效下做判断（假定真听出率 0.8），
  **大约需要每档 7 题**。所以先看结论卡的**总体**，再看三个分档 chip（详细模式分档 n = 10 / 6 / 4）。
- 真正能说明"听不出"的信号是**安慰剂题**上的表现：如果安慰剂上你也常常选"更好的一边"，
  那前面那些"听出差异"很可能只是猜测 —— 结论卡会把这一行标成黄色。
- 需要工具细节（Wilson 区间、p 值含义、每档 < 3 题为何无法判定）就展开「统计口径与样本量说明」，
  里面还有一段可复制的纯文本结论。
- 想得到更硬的结论：把 `app.py` 顶部的 `DETAILED_TEST_TOTAL`（或 `SHORT_TEST_TOTAL`）调大 ——
  每档题数随之增加，码率阶梯会自动循环，不需要改任何 API。

## 常见问题

**导入后没有声音？** 如果后端跑在 WSL 等没有音频设备的虚拟机里，是正常的 —— 在宿主机浏览器里打开
<http://localhost:8000> 即可。

**导入被拒绝？** 检查是否为无损格式、采样率是否 ≥ 44.1 kHz、时长是否 ≥ 30 秒；错误信息会说明具体原因。

**封面会不会出问题？** 不会。导入与切片都显式只取音频流，内嵌封面（附带的图片流）会被丢掉。
早期版本在"最佳片段正好从 0 秒开始"时会因为封面流报 `rc=234`，已修并有回归测试。

**首次开始测试要等多久？** 22 题详细模式首轮实测 15.8 秒（截片段 + 生成 20 档 MP3 + 响度/对齐校准），
之后同素材**直接复用缓存**（0.01 秒），界面会显示「新生成 0 / 复用 22」。

**点「查看答案」没反应 / 按钮消失了？** 那是浏览器还在跑缓存里的旧脚本（旧脚本读的字段已经改名）。
现在 `/` 与 `/static/*` 都带 `Cache-Control: no-cache`，页面用 `?v=N` 引用资源，正常情况下刷新一次就好；
万一还遇到，按 **Ctrl+Shift+R** 强刷即可 —— 揭晓函数本身也会给出这句提示，不会再静默失败。

**看清了答案还能改吗？** 不能，首答即最终 —— 否则可以先用「听不出」偷看码率再改成正解。
重复提交相同的选项是幂等的，页面按钮作答后也会禁用。

**"会话已失效"？** 后端重启或超过 2 小时未完成会丢弃会话，重新开始即可。

**删不掉音频？** 有进行中的测试在引用它，先结束测试。
