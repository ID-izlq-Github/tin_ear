# TinEar

**本地音频盲测工具 —— 你能听出 MP3 码率的区别吗？**

A local blind test for MP3 bitrate perception.

TinEar 把你自己音乐库里的无损片段切成 15 秒，生成不同码率的 MP3 版本，
再把**无损版**和**压缩版**做成一组等响度、精确对齐的 A/B 让你盲听 ——
你不知道哪边是无损，程序也不告诉你码率、文件名、编码器。

---

## 快速开始

```bash
cd tin_ear

make install     # 把依赖装进本项目专用 conda 环境 tin_ear（只需一次）
make run         # 前台启动，监听 0.0.0.0:8000（Ctrl+C 停止）
```

不想占着终端就用后台方式：

```bash
make run-bg      # 后台启动，日志写 data/server.log
make stop        # 停止
```

然后在 **Windows 浏览器**打开 <http://localhost:8000>（WSL 不出声，必须在 Windows 侧播放）。

`make help` 可看全部目标。等价的手工命令：

```bash
PIP_CACHE_DIR="$PWD/.pip-cache" TMPDIR="$PWD/data/tmp" \
  ~/miniforge3/envs/tin_ear/bin/python -m pip install -r requirements.txt

TMPDIR="$PWD/data/tmp" \
  ~/miniforge3/envs/tin_ear/bin/python -m uvicorn app:app --host 0.0.0.0 --port 8000 --workers 1
```

### 环境纪律

- Python 依赖**只**装进本项目专用 conda 环境 `tin_ear`；不碰 `base`、不碰其他项目环境、
  不 `apt install`、不 `npm -g`、不 `pip --user`。
- pip 下载缓存放在项目内 `.pip-cache/`；所有临时文件放在项目内 `data/tmp/`
  （`TMPDIR` + `tempfile.tempdir` 双重保证），不写系统 temp 或 `~/.cache`。
- 依赖全是 wheel（`soundfile` 自带 libsndfile），不需要编译器或系统库；ffmpeg/ffprobe 用系统已有的。

## 使用流程

1. **导入音频**：点「导入音频」选文件。只接受无损格式（FLAC / WAV / AIFF / ALAC / WavPack / TTA），
   要求采样率 ≥ 44.1 kHz、时长 ≥ 30 秒。导入后统一转成 48 kHz 立体声 FLAC。
   MP3 / AAC / OGG / Opus 会被拒绝并给出明确原因。同一段音频（即使换了容器格式）按内容哈希去重。
2. **选素材**：勾选 1～3 段，选「快速（6 题）」或「详细（12 题）」。
3. **开始盲测**：首次会截取片段、生成并校准压缩版（十几秒），之后同素材再测几乎瞬时开始。
4. **听**：点 A / B 试听（循环播放，切换时**保持播放位置**），然后选「A 更好 / B 更好 / 听不出」。
5. **确认后再走**：作答后**停在本题** —— 你的选择会高亮打勾、其余变暗，显示「已记录：B 更好」。
   这时可以点「查看答案」手动揭晓（默认不自动揭晓，避免对后面几题产生反馈偏置），
   再点「下一题 →」继续（最后一题是「查看结果 →」）。
6. **看结果**：分档正确率 + 95% 置信区间、逐档明细、安慰剂「听不出」比例、一句话结论。

键盘（测试页）：`1` = A 更好、`2` = B 更好、`3` = 听不出、`A`/`B`/空格 = 切换试听、回车或空格 = 下一题。
音频没载入完时三个选项是禁用的，避免在没听到声音时作答（保证反应时间有效）。

### 听测注意事项（重要）

- 关闭 Windows 音效增强、Dolby、EQ、空间音频、音量均衡。
- 系统音量固定，测试过程中不要再调。
- 用同一副耳机/音箱，从低码率题开始适应；疲劳了就停。
- 若页面顶部出现"设备实际采样率不是 48 kHz"的黄色警告，说明浏览器正在重采样，可能削弱可听差异。

## 数据与存储

```
data/
  library/   持久：48 kHz FLAC 母版 + index.json（含源文件元信息）
  cache/     持久：<audio_id>/meta.json、seg_*.flac、stimuli/v1/*.wav
  session/   临时：当前测试的硬链接，/api/end 或重启即清
  tmp/       临时：上传落盘与 ffmpeg 中间文件，重启即清
```

- 缓存体积上限约 **每首 130 MB**（2 段 × (11 档 + 1 安慰剂) × 5.76 MB）。界面上的
  「清理刺激缓存」会清空 `data/cache/`（库里的音频不受影响，下次测试重新生成）。
- `/api/end` 只删 session 里的硬链接，不动刺激缓存 —— 所以「再测一次」很快。
- **只有尚未完成的测试**会阻止删除（返回 409）；答完全部题目、或结束测试之后就能删。
  离开测试页、点「再测一次」、关闭标签页都会自动结束会话，不会留下"进行中的引用"。
- 测试进行中点「清理刺激缓存」是安全的：session 里是硬链接，已载入的音频照常播放；
  只是那轮结束后 session 目录会临时占用约 60 MB，结束测试即释放。

## 设计要点（为什么结果可信）

| 关注点 | 做法 |
|---|---|
| **响度线索** | 两路各自按 integrated loudness 独立增益到 −23 LUFS → 响度差恒为 **0**；再施加以对为单位的**共同**线性衰减把 True Peak 压到 ≤ −1 dBTP。全程**不使用限幅器**（限幅是非线性处理，会在低码率制造与 MP3 无关的失真线索） |
| **时间对齐** | FFT 互相关粗估 + 逐点平均绝对差精修，正负延迟都覆盖；两路统一裁到**精确 720000 采样**（48 kHz × 15 s 恰好 = 625 个 MP3 帧） |
| **信息泄漏** | `/api/audio` 只用随机不透明 token；响应键集合固定；两路 `Content-Length` 恒等。码率、编码器、文件名、是否安慰剂都不出现在前端 |
| **安慰剂** | 1～2 道题的 A/B 是**同一片段的两份无损拷贝**。若你在这类题上仍"听出更好的一边"，说明存在瞎猜倾向，结论会提示 |
| **片段选择** | 15 秒窗 / 5 秒步长滑动，按「响度标准差 + 谱通量 + 瞬态密度 − 静音比例」四分量 z-score 加权选段，偏好动态大、瞬态多、不安静的段落 |

## 测试

```bash
make test    # 46 项，约 1 分钟
```

- `tests/test_pipeline.py`：常量守护、对齐符号与真实 MP3 往返、等响度/峰值、
  **增益必须是纯线性**（防止有人塞进限幅器）、切片逐采样精确、片段选择确定性、缓存版本失效。
- `tests/test_api.py`：导入与去重、有损格式拒绝、删除与 409、参数校验、
  **防泄漏**、安慰剂两路相同、作答幂等、结果统计、启动/TTL 清理、路径穿越。
- 测试产物全部落在 `data/tmp/`（受 `TMPDIR` 约束）。

## 怎么读结果

- **逐档只有 1 道题**（默认题量下每档 1 题），所以逐档正确率只有 0% 或 100%，表格里会标注「样本不足」。
- 真正有意义的结论来自**分档聚合**（`≤96` / `128–192` / `≥224 kbps`）与 Wilson 95% 区间：
  区间下界 > 50% 才算"能可靠听出"。
- 想得到统计上更硬的结论，就把 `app.py` 顶部的 `DETAILED_TEST_TOTAL`（或 `SHORT_TEST_TOTAL`）调大 ——
  码率阶梯会自动循环重复，不需要改任何 API。

## 常见问题

**导入后没有声音？** WSL 不出声是正常的，必须在 Windows 浏览器里打开 <http://localhost:8000>。

**导入被拒绝？** 检查是否为无损格式、采样率是否 ≥ 44.1 kHz、时长是否 ≥ 30 秒；错误信息会说明具体原因。

**首次开始测试要等十几秒？** 在截片段 + 生成 10 档 MP3 + 做响度/对齐校准。之后同素材秒开。

**"会话已失效"？** 后端重启或超过 2 小时未完成会丢弃会话，重新开始即可。

**删不掉音频？** 有进行中的测试在引用它，先结束测试。

## 非目标

不做 ABX、不做自适应难度、不做账号/多用户/持久历史、不做 AAC/Opus 对比、不做动态片段长度、
不引入前端框架或构建工具、不使用数据库。
